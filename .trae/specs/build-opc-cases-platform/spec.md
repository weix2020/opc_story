# 全球 AI 相关 OPC（一人公司）成功案例库 Spec

## Why

"一人公司（One-Person Company）"在 AI 工具加持下从概念变成可复制的商业路径，但全球范围内公开、可核验、可结构化对比的 **AI 相关**案例集合仍然稀缺——散落在播客、独立开发者社区、媒体报道与融资数据库里，缺少统一的分析口径。本项目要做一个以**信源可核验**为核心差异化的案例库站点：50 个全球 **AI 驱动**的 OPC 成功案例，每个案例都讲清来龙去脉、历时演进、横向对标，并落到产品、客群、痛点、营收、融资、评价、成本与合规风险七个维度。

## What Changes

* 新建一个**纯静态**内容站点（Astro + TypeScript，输出 `dist/`），可直接部署到 Cloudflare Pages

* 首页为 50 个 OPC 案例的列表（标题 + 简介），卡片右下角展示**阅读量 / 点赞量 / 分享量**三个数值

* 列表默认排序规则：**上线时间降序优先，时间相同时按阅读量降序**

* 每个案例有独立详情页，含速览、来龙去脉、历时性分析、共时性横向对标、七维深度分析、逐条信源与核验说明

* 新增方法论页（信源类型、置信度分级、估算方法、争议记录规则）

* 全部数据落地为 `src/content/projects/*.md`（结构化 frontmatter + Markdown 正文），由内容集合 schema 在构建期强校验

* 新增内容校验脚本（`scripts/validate-content.mjs`），检查字段完整性、信源数量与独立性、七个维度与必备章节是否齐备

* 新增 Cloudflare Pages 部署说明与可选的计数后端（Pages Function + KV，env 开关控制，默认关闭）

**BREAKING**：无（全新项目，无既有接口或数据契约）

### 明确的口径定义（避免歧义）

| 术语        | 定义                                                                    |
| --------- | --------------------------------------------------------------------- |
| OPC       | One-Person Company：由单一创始人创立并主导，早期由单人运营的公司。允许后续扩编，但必须在案例中标明扩编时点与当前团队规模 |
| **AI 相关（硬性门槛）** | 案例的**核心产品或核心能力必须由 AI 驱动**，满足以下任一：① **ai-native**：产品本体即 AI 产品（AI 生成、AI Agent、AI 助手、AI 基础设施、AI 开发者工具等）；② **ai-embedded**：产品主体非 AI，但关键功能由 AI 支撑，且 AI 是其差异化与价值来源；③ **ai-enabled-ops**：非 AI 产品，但由单人 + AI 工具链完成从 0 到 1 并跑通商业化（AI 使一人团队得以成立）。每篇案例须在速览中标注其 AI 契合类型，并说明 **AI 在产品中的具体作用**。不满足者一律不收录 |
| "时间"（排序键） | `launchDate`：项目首次公开上线 / 对外可见的日期；无明确公开记录时回退为公司注册年份，并在卡片上标注"年份级精度"      |
| 年化营收      | 一律为**推算值**，必须写明推算方法与依据（定价 × 付费用户量 / 支付额截图 / 创始人公开表述 / 流量×转化率等），并标注置信度 |
| 阅读/点赞/分享  | 三类计数指标。默认使用站点种子值 + 浏览器本地覆盖层；可选接入 Cloudflare KV 实时后端                   |

## Impact

* Affected specs: 案例内容规范（信源核验协议、七维模板）、列表与排序契约、详情页信息架构、部署与计数链路

* Affected code: 全新仓库，无既有代码；影响面为 `src/**`、`scripts/**`、`public/**`、`astro.config.mjs`、`package.json`

* Affected data: `src/content/projects/*.md`（50 篇，全部为 AI 相关案例）、`src/content/methodology.md`、`data/pool.md`（候选池，含 AI 契合类型判定）、`data/research-log.md`（检索与核验日志）

## ADDED Requirements

### Requirement: 案例收录标准与候选池

系统 SHALL 以书面标准筛选案例，并保留候选池与淘汰记录。

#### Scenario: 建立候选池

* **WHEN** 研究阶段启动

* **THEN** 在 `data/pool.md` 中沉淀 ≥60 个候选项目，逐条记录：名称、创始人、总部、成立年份、官网、类别、**AI 契合类型（ai-native / ai-embedded / ai-enabled-ops）与 AI 作用一句话说明**、初步入选判定、来源 URL

* **AND** 其中 ≥50 个通过全部收录标准进入正式采集

#### Scenario: 收录标准

* **WHEN** 评估某个候选项目

* **THEN** 该项目必须同时满足：① **核心产品或核心能力由 AI 驱动**（符合 ai-native / ai-embedded / ai-enabled-ops 之一）；② 单一创始人创立且早期单人运营；③ 有公开可验证的商业成功证据（营收 / 用户量 / 流量 / 融资 / 并购 / 显著产品影响力）；④ 面向全球市场或具有全球参考价值；⑤ 公开信息量足以支撑七维分析与信源交叉验证

* **AND** 不满足标准的候选必须记录淘汰原因；因"非 AI 相关"被淘汰的候选需单独归类统计

### Requirement: AI 相关性判定

系统 SHALL 对每个案例明确判定其 AI 相关性，并在详情页与列表页可见。

#### Scenario: 标注 AI 契合类型

* **WHEN** 渲染任一案例

* **THEN** 速览区展示该案例的 AI 契合类型标签（ai-native / ai-embedded / ai-enabled-ops），并给出一句"AI 在产品中的具体作用"说明

* **AND** 正文"产品功能"维度中必须说明 AI 所承担的具体功能环节、所用技术路线（模型 API / 自研模型 / 微调 / RAG / Agent 工作流等）与 AI 对产品的价值贡献

#### Scenario: AI 相关性可被复核

* **WHEN** 用户查看某案例的"产品功能"维度

* **THEN** 该节包含指向 AI 能力具体证据的引用编号（指向信源列表中的一手或可靠二手信源），使 AI 相关性判断本身可被核验

#### Scenario: 列表页筛选

* **WHEN** 用户在首页按 AI 契合类型筛选

* **THEN** 列表仅保留匹配该类型的案例，且筛选后排序规则保持有效

#### Scenario: 候选池 AI 覆盖度

* **WHEN** 候选池筛选完成

* **THEN** 50 个正式案例中，ai-native 类型的数量不少于 30 个，其余由 ai-embedded / ai-enabled-ops 补足；不足时须在 `data/pool.md` 补充候选后重新筛选

### Requirement: 信源核验协议

系统 SHALL 对每个案例的每条关键信息执行信源核验，并在页面上可追溯。

#### Scenario: 信源数量与独立性

* **WHEN** 采集任一案例

* **THEN** 该案例至少拥有 5 条信源，且其中至少 1 条为**一手信源**（创始人自述、官方站点/官方博客/官方新闻稿、本人访谈原始记录）

* **AND** 至少 2 条来自**彼此独立**的机构或作者（转载、聚合站、同一次采访的多处转载不计为独立）

#### Scenario: 关键数字的交叉验证

* **WHEN** 写入营收、融资、用户量、流量等关键数字

* **THEN** 该数字必须由 ≥2 条独立信源支持；无法满足时必须标注为"单一来源/未交叉验证"并降级置信度

* **AND** 不同信源数据冲突时，必须同时保留双方数值、标明各自来源，并写入该案例的"争议与不确定性"段落

#### Scenario: 置信度分级

* **WHEN** 对任一数据点赋值

* **THEN** 使用 A / B / C 三级：A = 官方或可独立验证；B = 单一可信媒体或多方口径一致；C = 推算、访谈口径或社区传闻

* **AND** C 级数据必须在正文中显式标出推算方法

#### Scenario: 信源条目结构

* **WHEN** 渲染信源列表

* **THEN** 每条信源显示：编号、标题、发布方、发布日期、访问日期、类型（primary / secondary / database / aggregator / community）、直达链接

* **AND** 正文中的关键论断通过编号引用锚定到对应信源

### Requirement: 案例详情页信息架构

系统 SHALL 为每个案例提供统一的分析结构，覆盖历时性与共时性两个视角。

#### Scenario: 速览卡片

* **WHEN** 打开详情页

* **THEN** 首屏展示：一句话定位、创始人、成立与上线时间、总部/所在地、当前团队规模、营收预估、融资状态、官网链接、类别标签、**AI 契合类型标签**、**AI 作用一句话说明**

#### Scenario: 来龙去脉

* **WHEN** 阅读详情页

* **THEN** 以"起点/触发事件 → 冷启动 → 关键转折 → 当前状态"的叙事讲清前因后果

* **AND** 附时间线表格（日期 / 事件 / 对应信源编号），时间精度不足时明确标注

#### Scenario: 历时性分析

* **WHEN** 阅读详情页

* **THEN** 将项目历程划分为若干阶段，每阶段说明目标、关键动作、结果与对应信源

#### Scenario: 共时性横向对标

* **WHEN** 阅读详情页

* **THEN** 以表格形式与 3–6 个同赛道或同体量项目对比：成立时间、团队规模、变现模式、定价、营收规模、融资状态、增长信号

* **AND** 表格中每个项目的对比数据标注信源编号，无法核实的单元格写"未公开披露"

#### Scenario: 七维深度分析

* **WHEN** 阅读详情页

* **THEN** 必须存在且仅聚焦以下七个维度：产品功能、面向客群、解决痛点、预估年化营收、融资进展、市场评价、投入成本与合规风险

* **AND** 每一维为独立小节，营收维含推算方法，市场评价维同时呈现正面与负面评价及出处，成本与合规维区分"投入成本结构"与"合规/法律/IP/数据风险"

* **AND** "产品功能"维度必须包含 **AI 能力说明**：AI 承担的功能环节、技术路线、模型来源（第三方 API / 自研 / 开源模型微调）、以及 AI 对产品价值与一人团队成本结构的贡献，并附引用编号

* **AND** "投入成本与合规风险"维度需专门说明 **AI 带来的增量成本与增量风险**（模型调用与推理成本、模型供应商依赖与限流、训练数据版权、生成内容合规、内容标识与版权署名、数据隐私、监管适用性）

#### Scenario: 缺失数据的处理

* **WHEN** 某维度无可靠公开信息

* **THEN** 明确写"未公开披露"并说明检索范围与检索时间，不允许用推测填充

### Requirement: 案例列表与排序

系统 SHALL 提供首页列表，遵守指定排序规则。

#### Scenario: 列表项内容

* **WHEN** 访问首页

* **THEN** 每个列表项展示项目标题、一句话简介、上线时间、类别标签、**AI 契合类型标签**，并在**卡片右下角**展示阅读量、点赞量、分享量三个数值

#### Scenario: 默认排序

* **WHEN** 首页完成首次渲染

* **THEN** 案例按 `launchDate` 降序排列；当多条案例 `launchDate` 相同或仅精确到年份时，按阅读量降序排列

#### Scenario: 计数一致性

* **WHEN** 用户在浏览器内产生新的浏览/点赞/分享事件

* **THEN** 计数在本地生效后，列表仍按"时间降序 → 阅读量降序"重新排序，顺序不出现前后矛盾

#### Scenario: 检索与筛选

* **WHEN** 用户在首页输入关键词、选择类别或选择 AI 契合类型

* **THEN** 列表即时过滤，且计数面板与排序规则保持有效

### Requirement: 指标计数链路

系统 SHALL 提供可部署环境下真实生效的计数能力，并在离线/未配置时保持可用。

#### Scenario: 默认本地模式

* **WHEN** 站点未配置远程计数端点

* **THEN** 计数以内容文件中的种子值为基线，叠加浏览器本地增量（浏览按会话计一次、点赞可切换、分享按钮触发计数），刷新后保留本地状态

#### Scenario: 远程模式

* **WHEN** 配置了 Cloudflare Pages Function 计数端点（KV 绑定）

* **THEN** 浏览/点赞/分享事件上报到该端点并写入 KV，页面展示服务端聚合值，本地覆盖层与远端值合并显示

#### Scenario: 计数接口契约

* **WHEN** 调用计数端点

* **THEN** 支持读取（项目 slug → 三项计数值）与写入（slug + 计数字段 + 增量），写入具备基本防刷（同一 slug + 事件类型限频）

### Requirement: 内容校验与构建期失败

系统 SHALL 在构建期拦截不合规内容，避免残缺案例上线。

#### Scenario: 字段级校验

* **WHEN** 构建站点

* **THEN** 内容集合 schema 对标题、简介、创始人、`launchDate`、类别、**AI 契合类型（枚举）**、AI 作用说明、计数种子、七维要点、信源数组等字段做类型与必填校验，字段缺失或类型错误直接导致构建失败

#### Scenario: 内容级校验脚本

* **WHEN** 执行 `npm run validate`

* **THEN** 脚本逐篇检查：信源数量 ≥5、一手信源 ≥1、独立信源 ≥2、七个维度小节齐备、**AI 契合类型在 ai-native / ai-embedded / ai-enabled-ops 之内且 AI 作用说明非空**、历时性阶段与横向对标表格存在、正文引用编号能对应到信源列表

* **AND** 校验不通过时以非零退出码结束并列出具体文件与问题

#### Scenario: 校验接入构建流程

* **WHEN** 执行 `npm run build`

* **THEN** 构建前自动执行内容校验，校验失败则不产出 `dist/`

### Requirement: 部署与交付

系统 SHALL 产出可直接部署到 Cloudflare 的静态站点及部署说明。

#### Scenario: 静态产物

* **WHEN** 执行 `npm run build`

* **THEN** 在 `dist/` 生成完整静态站点，含首页、50 个案例详情页、方法论页、404 页、站点图标与缓存/安全响应头配置

#### Scenario: Cloudflare Pages 配置

* **WHEN** 按部署文档在 Cloudflare Pages 建立项目

* **THEN** 构建命令为 `npm run build`，输出目录为 `dist`，Node 版本 22，站点可直接通过 Pages 域名访问

#### Scenario: 部署文档

* **WHEN** 查阅部署说明

* **THEN** 包含 Pages 项目创建步骤、环境变量说明、KV 计数后端可选启用步骤、以及本地预览与校验命令

### Requirement: 方法论页

系统 SHALL 提供方法论页，公开本案例库的收录口径、AI 相关性判定标准与信源规则。

#### Scenario: 方法论页内容

* **WHEN** 用户访问 `/methodology`

* **THEN** 页面说明：OPC 定义与"一人 + AI"的判定口径、**AI 相关性三分法（ai-native / ai-embedded / ai-enabled-ops）及判定示例**、信源类型划分、A/B/C 置信度分级、营收推算方法、数据冲突处理规则、"未公开披露"原则、检索截止时间

## MODIFIED Requirements

无（全新项目）。

## REMOVED Requirements

无（全新项目）。

## Out of Scope

* **非 AI 相关的 OPC 案例**（无论营收规模多高，均不收录）
* 用户账号、登录、评论、订阅等需要后端持久化的功能
* 站内全文搜索引擎（仅首页客户端过滤）
* 国际化 / 多语言版本（本期仅中文）
* 案例数超过 50 的扩充（本期固定 50）
* 实时第三方流量数据的自动接入（流量数据以检索时点的核验快照写入正文并标注采集时间）
